# 聖天包裹 JSON 預報腳本

[安裝／更新聖天腳本](https://github.com/DF-wu/taobaoOrderExporter/raw/main/shengtian-predeclare.user.js) · [回到專案說明](../README_zh-Hant.md)

在聖天「我的包裹」頁貼上 JSON 或匯入 JSON 檔，先核對目前包裹與歷史集運紀錄，再逐筆預報。每筆提交後，腳本會從服務端重新讀取單號、品名、備註及數量，確認相符才算成功。

## 安裝與操作

1. 在 Brave／Chrome／Firefox 安裝 Tampermonkey 或 Violentmonkey，開啟上方安裝連結。初版版本為 `1.0.0`。
2. 登入聖天，開啟 [我的包裹](http://member.stjh168.com/Member/MyPack)。腳本會在頁面加入預報面板。
3. 貼上 JSON 或選擇 `.json` 檔，再按「匯入 JSON」。檢查預覽中的單號、品名、備註、數量及商品對應；取消勾選這次不處理的包裹。
4. 按「檢查已預報（只讀）」，核對哪些單號已有資料、歷史已集運、可新增或可補報。這一步只查詢，不登記包裹。
5. 檢查品名及備註，完成需要的「已核對」勾選後，按「開始／續跑預報」。腳本逐筆處理並保存結果，可按「停止」後續跑。
6. 按「匯出結果 JSON」，查看逐筆結果及「來源例外／輸入重複」。結果待核對的包裹需要先釐清，不能直接重送。

請求間隔預設 `1.5` 秒，可在面板調為 `1–30` 秒。匯入每批最多 5,000 筆來源；檔案大小上限為 10 MiB，超過時先拆批。

安裝後一般操作不需要開啟 debug port，也不需要執行 Node 或 Python。此腳本只讀 JSON；XLSX 可先用 repo 內的 [轉換工具](../skills/shengtian-predeclare/scripts/read_export.py) 轉成 JSON。

## JSON 格式

所有範例都是合成資料。快遞單號及訂單號一律使用字串，保留前導零與長 ID；數字型單號會被拒絕，不會轉成字串猜回原值。

### 簡單包裹清單

適合已整理好品名與備註的資料，可直接貼上陣列：

```json
[
  {
    "trackingNumber": "JT0000000000001",
    "goods": "打印板",
    "memo": "[1234567890123456789]+[示例店舖打印板]",
    "number": 1
  },
  {
    "trackingNumber": "001234567890123456789",
    "goods": "甲片、果冻胶",
    "memo": "[1234567890123456790]+[示例甲片、果冻胶]",
    "number": 1
  }
]
```

也可使用 `{ "packages": [...] }` 包裝同一份陣列，或匯入既有聖天工具產生的 `{ "entries": [...] }` 計畫。計畫若含 `accountMarker`，必須與目前登入帳號相符。

| 欄位 | 用途 |
| --- | --- |
| `trackingNumber` | 必填；8–40 個英數字的完整單號字串。會移除前後空白並轉成大寫，不接受中間空白或遮蔽符號。 |
| `goods` | 送到聖天的簡短貨物品名。缺少時需在預覽中填寫後再預報。 |
| `memo` | 備註原文；可保留主訂單號及店舖／品牌，供後續對帳。 |
| `number` | 聖天表單的數量，預設 `1`；必須是 JSON 正整數，字串 `"1"` 不合格。不會把淘寶商品件數自動加總。 |

品名與備註不接受控制字元或尖括號 `<`、`>`。數量範圍為 `1–2147483647`。

同一單號的完全相同資料會合併。品名、備註或數量不同的重複資料會列為「輸入衝突」；先核對所有來源，修正預覽內容並勾選「已核對」，或修正 JSON 後重新匯入。

### 淘寶匯出 JSON

可直接匯入本 repo 淘寶匯出器的 `schemaVersion: 1` JSON。腳本會整理 `orders[].packages[]`，保留來源主訂單號、店舖、商品及規格，並按快遞單號合併。

淘寶商品標題可能很長，SKU 也可能代表另一種實際商品。腳本不會把未核對的標題自行改成報關品名：未提供品名的包裹，需要在預覽中填入準確簡稱並勾選「已核對」。也可在原匯出 JSON 加上 `declarations`，按單號提供已核對的資料：

```json
{
  "schemaVersion": 1,
  "orders": [
    {
      "orderId": "1234567890123456789",
      "shopName": "示例店舖",
      "items": [
        {
          "subOrderId": "1234567890123456790",
          "title": "示例打印板商品",
          "sku": "PEI 打印板"
        }
      ],
      "packages": [
        {
          "trackingNumber": "JT0000000000001",
          "company": "示例快遞",
          "subOrderIds": ["1234567890123456790"]
        }
      ],
      "logisticsStatus": "complete"
    }
  ],
  "declarations": {
    "JT0000000000001": {
      "goods": "打印板",
      "memo": "[1234567890123456789]+[示例店舖打印板]",
      "number": 1
    }
  }
}
```

沒有自訂備註時，預覽會保留來源主訂單號與店舖。多個主訂單共用同一快遞單號時，只預報一次並保留各來源訂單的對照。

一筆淘寶訂單有多個包裹，但官方未提供商品對應或包裹商品描述時，腳本會要求核對包裹內容。請對照預覽中的來源資訊及官方物流資料，再勾選「已核對」；已在輸入前核對完成的資料，也可在該單號的 `declarations` 物件內加上 `"packageReviewed": true`。腳本不按陣列順序猜商品屬於哪個包裹。

有可匯入包裹時，沒有單號的來源訂單會列在「來源例外／輸入重複」，不送到聖天。若整份淘寶 JSON 都沒有有效單號，匯入會回報沒有可匯入的包裹。`not_required`／`no_package` 與查詢 `failed` 分別保留，不能把物流查詢失敗當成無需物流。

## 重複、已報、查無與未知結果

| 情況 | 腳本處理及後續操作 |
| --- | --- |
| 輸入有相同單號、相同內容 | 合併為一筆，避免重複送出。 |
| 輸入有相同單號、不同內容 | 顯示「輸入衝突」，修正後勾選「已核對」，或重新匯入。 |
| 目前包裹已有預報標記、品名或備註 | 顯示「已有資料」，保留已有紀錄。品名或備註只有部分內容也會保留供核對。 |
| 單號只存在歷史集運訂單 | 顯示「歷史已集運」，跳過新增。 |
| 已自動入庫，`Is_Yb=0` 且品名、備註皆空白 | 顯示「可補報」；儲存後回讀核對。 |
| 目前列表沒有，歷史查詢明確回傳零筆 | 顯示「可新增」。查無歷史不等於快遞單號錯誤。 |
| 服務端明確拒收、提示重複或查無資料，且確認資料未變 | 顯示「網站拒絕」、「網站回報重複」或「網站回報查無」，保留完整原因；修正 JSON 後重新匯入。 |
| 同一單號在服務端出現多筆 | 顯示「服務端重複」並停止，先人工核對。 |
| 提交逾時、斷線或收到未知回應 | 先回讀；未能確認時顯示「結果待核對」並停止，保留未完成紀錄，不自動重送新增。 |
| API 回報成功，但回讀內容不同、單號缺少或文字被截斷 | 不記成功，停止並保留差異。 |
| 登入過期、回傳登入頁、格式改變或帳號切換 | 停止；重新登入原帳號後先重新核對。 |

「停止」會停止送出後續包裹。若當時已有提交請求送出，腳本會先核對該筆結果；關閉頁面或瀏覽器中斷留下的提交紀錄，也會先列為未知結果處理。已送出紀錄的原始品名、備註及數量會凍結供回讀比對。即使匯入另一份 JSON，尚未釐清的提交紀錄仍會加入預覽，不會被新檔案取代。

把「匯出結果 JSON」帶到另一個瀏覽器匯入時，其中 `submitting`／`unknown` 的原始提交快照也會保留，只能先回查核對。網站回傳的重複／查無等原因以原文保留；中文關鍵字分類僅協助查看，不取代服務端回讀驗證。

只看到「提交成功」不算完成。成功條件是服務端回讀同一單號只有一筆，且品名、完整備註及數量與本次計畫相同。遇到未知結果，先使用只讀查詢重新核對；仍不明時，對照聖天頁面及下載結果處理。

備註過長時，腳本保留原文及服務端錯誤，不自行截短主訂單號或刪除來源對照。確認該次沒有寫入後，才縮短描述並重新整理計畫。網站的確切字數上限未確認。

## alert 處理與資料保存

官方頁面的提交處理使用同步 AJAX，之後呼叫原生 `alert` 並重新整理整頁。腳本改用同源 `fetch` 呼叫相同的預報端點，逐筆判斷回應，再讀回儲存結果，因此不會觸發這條前端 alert／reload 流程。網站其他功能的 `alert`、`confirm`、登入提示及彈窗照常運作。

聖天目前會對提交文字多做一次 URL decode。腳本先跳脫 `%` 與 `+`，再做一般表單編碼；儲存後逐字比對原文，避免 `+` 變成空白或把 `%2B` 留在備註中。這是該站的處理方式，不能直接套用到其他網站。

輸入、佇列、提交紀錄及錯誤保存在目前聖天來源的 IndexedDB，依登入帳號隔離。跨分頁鎖避免同帳號兩個腳本任務同時提交；聖天目前使用 HTTP，腳本不依賴僅在安全來源可用的 Web Locks API。重新整理後可恢復本機進度，瀏覽器清除網站資料則會移除本機紀錄，請下載結果備份。

腳本沿用已登入頁面的 session，不讀出或匯出 Cookie，不把包裹資料傳到其他網站。只讀查詢會把單號送到聖天核對；開始預報才會送出選定包裹的品名、備註及數量。腳本不申請打包、不付款、不刪除已有包裹。

## 驗證範圍與維護

2026-10-28 已在登入的 Brave 頁面核對表單、官方前端腳本、目前包裹 API 及歷史查詢結構。開發驗證採真實頁面的只讀查詢與攔截寫入的模擬測試；沒有為了測試而建立任意真實包裹，也沒有把之前的淘寶匯出資料整批送出。

1.0.0 的合成核心測試涵蓋 27 種情況，包含未知結果跨瀏覽器匯入、先保存再寫入、完整文字回讀及停止時的進行中請求。隔離瀏覽器另核對成功新增、空白入庫補報與 ID 保留、已有／歷史紀錄、斷線、成功提示卻無資料、服務端多筆同號、重整及重新匯入後仍不重送、跨分頁互斥；提交流程沒有產生原生 alert。

預報端點與欄位沿用 repo 中 [聖天流程實測紀錄](../skills/shengtian-predeclare/references/site-workflow.md)。它們是網站當前實作，並非官方承諾固定的公開 API。網站改版、回應格式異常或回讀不符時，腳本會停止，應先更新解析與測試再續跑。

需要 agent 代為核對 XLSX、產生簡短品名並操作既有 Brave debug 連線時，可使用 [聖天預報 skill](../skills/shengtian-predeclare/SKILL.md)。userscript 與 skill 各自保存進度；兩者都以聖天服務端的現有紀錄為準。
